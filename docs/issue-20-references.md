# 이슈 #20 참고자료 정리 — 2026-10-27

이슈 #20(사이트 문구 다듬기)에 레퍼런스로 달린 글 두 편의 요약과, 이슈 작업 항목과의 대응을 정리한다.
요약은 글 본문을 읽고 정리한 것이며, 두 글 모두 이미지로만 제시된 예시는 확인하지 못했다.

## 1. 신입 개발자 포트폴리오 작성법 (velog, yoosion030)

글쓴이는 9개월간 약 60개 기업에 지원해 8곳에서 서류 합격 연락을 받았고, 내용은 "정답이 아니라 본인 경험에서 나온 방법"이라고 밝힌다.

### 핵심 관점
- 포트폴리오는 면접으로 가는 발판이다. 회사가 실적을 낼 수 있는 사람인지 판단할 **근거**를 보여줘야 한다.
- 포트폴리오는 "내 커리어를 15초간 설명하는 티저"다. 남의 양식을 따르기보다 자기 커리어를 보여준다.
- 웹 URL로 포트폴리오를 두고, PDF 제출용 이력서는 따로 만들었다.

### 섹션별 조언

| 섹션 | 권장 | 피할 것 |
|------|------|---------|
| 자기소개 | 가치관은 짧게 요약하고 성과와 엮는다. 자세한 가치관은 면접에서 말한다 | 가치관 위주의 긴 소개 |
| 프로젝트 | 처음 보는 사람 기준으로 쓴다. 페이지의 역할·기능과 어려웠던 점을 함께 쓴다. 화면 캡처를 붙인다. 여러 사람에게 보여 피드백을 받는다. 트러블슈팅 섹션을 넣는다(신입은 필수라고 봄) | "00 페이지 개발", "00 기능 개발"처럼 무엇인지·무엇이 어려웠는지 알 수 없는 표현. 내가 아는 키워드만 쓰는 것 |
| 기술 | 기술별 **경험**을 쓴다. 자신 있는 기술을 위에 둔다. 남들도 할 법한 경험보다 나만의 경험을 쓴다. 블로그·GitHub 링크로 뒷받침한다. 쓸 내용이 없으면 항목을 삭제해도 된다 | 상태바·레벨·숙련도 표시, "어느 정도 사용 가능" 같은 추상 표현 |

### 트러블슈팅 구조
- 글쓴이가 쓴 방식: 문제 → 해결 방법 → 이전 코드와 비교 → 알게 된 점
- 더 효과적이라고 제안한 방식: **문제 → 시도했던 방법들 → 비교 → 알게 된 점**
- 채용담당자는 "어떤 문제를 만나 무엇을 시도했고 어떻게 해결에 도달했는지", 즉 문제 해결 사고방식을 본다.

### 기술 스택에 채택 이유 쓰기 (선택 사항)
- 기술을 나열만 하던 방식에서 채택 이유를 함께 쓰는 방식으로 바꿨고, 면접관 질문이 말하고 싶은 경험으로 자연스럽게 이어졌다.
- 다만 서류 합격률 차이는 크게 느끼지 못했다고 직접 밝힌다.

## 2. 그런 개발자로 괜찮은가 — 이력서 편 (taetaetae)

### 핵심 관점
- 이력서는 남에게 알리는 도구이기 전에 "나를 가장 잘 아는 거울"이다.
- 쓰는 이유 두 가지: ① 개인 브랜딩(취업 기회·인적 네트워크), ② 자기 성찰(무엇을 했고 무엇이 부족한지 사실로 확인).

### 언제 쓰는가
- 업무나 도전이 마무리된 직후(기억이 가장 구체적일 때).
- 분기·반기 등 주기적으로. 쓸 내용이 없는 기간은 흘려보냈다는 신호다.

### 어떻게 쓰는가
- **심플함이 원칙**: 한 일을 나열하는 일기식 서술을 피하고 중요한 포인트만 간결하게 쓴다.
- 구성 순서: 서두(인사·자기소개 포인트) → 업무 경험 → 업무 외 경험 → 기술.
- 권장: **수치 제시**(고유 수치가 신뢰도를 높임), **참고 링크 첨부**, **외부 URL 공개**(읽는 사람을 의식하게 되어 더 신경 써서 쓰게 됨).
- 신중: 도표·이미지는 읽는 흐름에는 도움이 되나, 저자는 개발자 이력서에는 산만하다고 봤다.
